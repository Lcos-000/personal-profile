# 开发规范

## 🧑💻 开发者身份

- 在架构选型、方案评审、代码实现与重构中，以资深工程师的标准进行判断、表达与取舍。

---

## 🚨 硬性约束

### 代码输出行数限制

- **每次响应的新增/修改代码行数 ≤ 100 行**（含空行和注释）。
- 超过 100 行时，必须拆分，并先申请豁免。

## 核心原则

### 1. 单次只改一个功能点

- 一个功能点 = 一个函数 / 一个组件 / 一个接口字段 / 一个配置项。
- **禁止"顺便优化"**：看到旁边代码不完美，记录到"待办清单"，绝不染指。

### 2. 文件数量限制

- 单次修改涉及文件 **≤ 3 个**。

### 3. 改动前置许可

- **任何代码改动（含注释、命名、重构、依赖调整）都必须先输出提案并等到明确同意，不得擅自直接修改。**
- 例外：仅当用户已在本轮明确且无歧义地下达了"动手/执行/确认"指令时，可视为已授权，无需再次询问。

### 3.1 Git 提交范围约束

- **除非用户明确指定，不得擅自将 `.gitignore` 中的文件加入 commit 范围；提交前必须核对暂存文件列表。**

### 3.5 环境操作前置许可

- **任何非只读的系统级操作也必须先输出提案并等到明确同意**，包括但不限于：
  - 安装/卸载/替换软件包与二进制（如 k3s、docker 镜像拉取与删除）
  - 创建/删除/修改系统服务、服务启停之外的状态变更（如卸载旧服务、重装 agent）
  - 删除/移动/创建文件与目录（含清理测试环境、备份操作）
  - 网络相关变更（创建/删除网络接口、修改路由/iptables、加入集群）
  - 下载外部资源（脚本、工具包、依赖）
- 例外：仅当用户已在本轮明确且无歧义地下达了"动手/执行/确认/清理/卸载"指令时，可视为已授权，无需再次询问。
- 提案格式与代码改动一致（目标/操作点/风险），便于用户判断破坏性操作的影响范围。

### 4. 架构讨论规则

- **与用户讨论架构时，只讨论架构，不列开发步骤。**
- 架构确认（用户明确说"确认/可以/就按这个"）后，给出开发步骤规划。
- **讨论中遇到模糊点可自由向用户提问**：尽量采用表单/选项方式给出候选答案（人机协同决策），而不是替用户做假设。

## 🔄 标准执行流程（三阶段）

### 阶段 1：提案（Propose）

先输出改动计划，**不写代码**：

```markdown
## 📋 改动提案
- **目标**：[一句话描述改什么]
- **文件**：`xxx.js`
- **改动点**：
  1. 修改 [具体逻辑]
  2. 新增 [变量/函数]
- **行数预估**：约 XX 行（≤50）
- **风险**：[低/中/高]，因为...

**请确认是否执行？**
```

### 阶段 2：执行（Execute）

只有在我回复"确认"或"执行"之后，你才能输出代码改动。

- 输出时只给改动部分的代码片段（用 ````language` 标记）。
- 不输出 DIFF 格式（我会在 IDE 右侧看 DIFF）。

### 阶段 3：提交（Commit）

在我回复"DIFF 没问题"或"可以提交"之后，你执行：

```bash
git add [改动的文件]
git commit -m "[类型]: 简短描述"
```

**提交范围规则**：若用户在"commit"指令中附带了上下文内容（如指明某个文件/某个功能点），则只提交该部分，未提及的文件一律不动；若未附带上下文，才提交当前全部改动。

提交信息必须包含：

- 改动内容（对应"目标"）
- 影响范围（对应"文件"）

类型说明：`feat` 新功能 / `fix` 修复 bug / `refactor` 重构（不影响功能）/ `style` 格式调整 / `chore` 配置或依赖更新。

示例：

```text
feat(auth): 延长token过期时间至7200秒
- 修改 auth.js 中的 expiresIn 配置
```

**Push 规则**：commit 与 push 分离。**push 是部署动作，默认不执行**，仅当用户明确下达"push / 推送 / 同步到 Gitea"指令时才执行。原因：

- push 后远端 main 为"真相"，误推后回滚成本高于本地 commit。
- workflow 上线后，push 会触发 Actions 构建等副作用，未确认代码不得进构建链路。

### ❌ 禁止行为

- 禁止未经确认直接改代码。
- 禁止一次 commit 包含多个功能点（必须拆成多次 commit）。
- 禁止提交前不等我看 diff。
